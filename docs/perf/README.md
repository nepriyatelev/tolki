# Замеры производительности

## Нагрузочный тест: 15 участников и одна демонстрация (#33)

```sh
pnpm perf:load
```

Запускает организатора (настоящее приложение, он же участник через свой интерфейс) и 14 участников в отдельном Electron — по скрытому окну на каждого, с тем же кодом звонка, что в приложении (`src/renderer/src/room/call.ts`). Вместо микрофона у каждого ровный тон без пауз; организатор входит с выключенным микрофоном. Один участник показывает фейковое видео 1080p как экран. После 15 с разгона 30 с меряет сервер комнаты организатора (процесс host и mediasoup-worker) и пишет отчёт в [`load-15.md`](load-15.md) с цифрами против бюджетов PLAN §6.

Занимает около минуты; в CI не входит (тяжёлый, а цифры зависят от машины). Отчёт перезаписывается при каждом запуске — коммитить его после изменений, влияющих на производительность.

### Что этот тест уже нашёл
- **Задержка по TCP:** запасной канал ICE-TCP шёл через прокси на общем порту с включённым алгоритмом Нейгла. При оживлённой комнате это давало RTT ~176 мс вместо ~12 мс. Исправлено: `setNoDelay` на обоих сокетах (`src/host/server.ts`).
- **Смена голоса в замере (#96) — неточность самого теста:** фейковый микрофон Chromium пищит с паузами, а у организатора был включён настоящий микрофон компьютера, который то слышит комнату, то нет. Голос, молчащий дольше ~2 с, честно уступает слот, и изредка за замер у участника набиралось 4 голоса. Теперь у участников ровный тон, организатор без микрофона: смена голоса в замере означала бы ошибку выбора.
- **Перещёлкивание голосов:** когда говорят больше трёх человек одинаково громко, «тройка громких» менялась каждые 300 мс — голоса обрывались, а consumers постоянно вставали на паузу и снимались с неё. Исправлено: голос держит слот, пока говорит; уступает его только после ~2 с тишины (`src/host/speakers.ts`).

### Что здесь не мерится
- Клиентский бюджет (CPU ≤ 5 %, RAM ≤ 250 МБ), холодный старт, фон без звонка и аппаратный кодек экрана — ниже, #34.
- Реальный трафик экрана: фейковое видео почти не меняется и сжимается в сотни кбит/с; ориентир на реальном экране — ≈ 40 Мбит/с на 14 зрителей (PLAN §2).

## Бюджеты клиента (#34)

```sh
pnpm perf:budgets
```

Холодный старт (5 запусков со свежим профилем, от запуска до окна на экране), приложение без звонка (окно открыто и свёрнуто) и участник в голосовом звонке: слышит три голоса и говорит сам. Пишет [`budgets.md`](budgets.md). Около трёх минут.

Память считается как физический объём процессов (то, что показывает «Мониторинг системы» на macOS; PSS на Linux). Сумма RSS по процессам Electron примерно вдвое больше: общие страницы фреймворка, отображённые в каждый из ~5 процессов, в ней считаются по разу на процесс. По RSS бюджет 250 МБ «не проходил» (≈530 МБ), по реальному объёму — проходит (≈220 МБ).

## CPU показывающего экран (#34)

```sh
pnpm perf:share
```

Показывающий — отдельный Electron с кодом звонка приложения; «экран» — canvas 1920×1080, 60 к/с, с постоянным движением по всему кадру (худший случай для «Плавно»); смотрит организатор. То же рисование без отправки — база; разница — цена отправки. Пишет [`share-cpu.md`](share-cpu.md).

### Почему экран — два потока, а не simulcast
Замер до изменения (Apple M1 Pro, тот же стенд, цена кодирования сверх базы, % одного ядра):

| Как отправлять | Кодировщик | Цена |
|---|---|---|
| H.264 simulcast, 2 слоя (было) | OpenH264 ×2, программный | ≈ 61 % |
| VP8 simulcast, 2 слоя | libvpx ×2 | ≈ 62–130 % |
| H.264 один слой ≈1080p | VideoToolbox, аппаратный | ≈ 12 % |
| VP8 один слой ≈360p, 15 к/с | libvpx | ≈ 2 % |

Chromium кодирует simulcast только программно (`SimulcastEncoderAdapter`), а аппаратный кодировщик берёт лишь одиночный поток. Ещё одна находка: VideoToolbox не принимает профиль H.264 constrained baseline (`42e01f`), который стоял в комнате, — только baseline (`42001f`) и main; с `42e01f` даже одиночный поток уходил в OpenH264. Сейчас: комната с `42001f`, показывающий отправляет ≈1080p H.264 (аппаратно) и ≈360p VP8 отдельным потоком, организатор каждому зрителю пересылает один из них — по размеру окна и по оценке пропускной способности зрителя (`src/host/screen-layer.ts`).

Ещё одна деталь: у двух отправителей одной дорожки WebRTC берёт наименьшую частоту кадров из запрошенных, и ≈360p с 15 к/с держал бы ≈1080p на 15 к/с. Поэтому у потока ≈360p — свой клон дорожки.
